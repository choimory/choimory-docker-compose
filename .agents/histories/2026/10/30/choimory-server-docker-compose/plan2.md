# 모든 어플리케이션 다 작성한건가?

> 모든 어플리케이션 다 작성한건가?

## 답변

이번 범위로 정한 앱은 모두 작성함. 빠진 건 **백업(restic 또는 Kopia)** 하나뿐. 둘 중 무엇을 쓸지 아직 정하지 않아서 넣지 않음.

## Notion ⑤ 앱 목록과 비교

| 구분 | 앱 | 상태 |
| --- | --- | --- |
| 기반 | Docker + Docker Compose | 호스트에 설치하는 것이라 compose 대상이 아님 |
| | Dockge, Homepage, Uptime Kuma | 작성함 |
| 미디어 | Jellyfin | 작성함 |
| | Navidrome, Audiobookshelf | 제외 (선택 앱이라 이번엔 빼기로 결정) |
| 파일 / NAS | Samba | 호스트 apt 설치라 `samba/README.md`에 설정만 기록 |
| | Immich, File Browser | 작성함 |
| | Syncthing | 제외 (선택 앱이라 이번엔 빼기로 결정) |
| 기타 | Vaultwarden, AdGuard Home | 작성함 |
| | 백업 (restic 또는 Kopia) | **작성 안 함** |
| 개발 / 프로젝트 | Argo CD, DB, Redis 등 | k3s와 GitOps 쪽이라 이 저장소 범위가 아님 |

## 백업 선택지

- **restic**
  - CLI 도구라 보통 호스트에 apt로 설치하고 systemd timer로 주기 실행. compose가 아니라 Samba처럼 문서와 스크립트로 관리하게 됨
  - 가볍고 단순함
- **Kopia**
  - 웹 UI가 있는 서버 모드를 compose로 띄울 수 있음. 스냅샷 확인이나 복원을 화면에서 할 수 있음
  - restic보다 무거움

어느 쪽이든 Immich의 Postgres는 파일 복사가 아니라 `pg_dump`로 덤프를 떠서 `/data/backup`에 모은 다음 백업해야 함. 백업 대상은 다음과 같음

- `/data/apps`: 설정과 DB
- `/data/backup`: DB 덤프
- 필요하면 `/data/nas/photos`

## 결정이 필요한 것

1. **백업 도구**: Kopia와 restic 중 어느 쪽으로 할지
2. **백업 보관 위치**: 외부 디스크, 클라우드(B2, S3 등), 춘천 본가 PC 중 어디로 보낼지. 같은 디스크의 `/data/backup`은 진짜 백업이 아니라서 외부 보관 위치가 꼭 필요함

# restic vs kopia 너의 선택은

> restic vs kopia 너의 선택은

## 답변

**Kopia** 선택

## 이유

1. **이 저장소 구조와 맞음**: Kopia는 서버 모드를 compose로 띄울 수 있어서 `choimory-server/kopia/`에 다른 앱과 같은 방식으로 넣을 수 있음. restic은 호스트 설치에 systemd timer와 스크립트까지 따로 관리해야 함
2. **복원이 쉬움**: 백업은 결국 복원할 때 쓰는 건데, 혼자 운영하면 복원 명령어를 기억하기 어려움. Kopia는 웹 UI에서 스냅샷을 둘러보고 파일 하나만 골라 복원할 수 있음
3. **스케줄과 보존 정책 내장**: 일·주·월 단위 보존 정책과 압축을 Kopia 자체 설정으로 처리. restic은 cron/timer와 `forget --prune` 스크립트를 직접 짜야 함
4. **모니터링 가능**: Uptime Kuma로 Kopia 웹 서버가 살아 있는지 감시할 수 있음

## restic이 나은 경우

- 백업을 화면 없이 스크립트로 완전히 자동화하고 싶을 때
- 사용자층이 더 넓고 오래 검증된 도구를 원할 때

둘 다 암호화, 중복 제거, B2/S3 같은 저장소를 지원하므로 기능 차이는 크지 않음. 결국 운영 편의성 차이

## Kopia로 가면 정할 것

1. **백업 보관 위치**: 외부 디스크, 클라우드(B2, S3 등), 춘천 본가 PC 중 어디로 보낼지
2. **Immich DB 덤프 방식**: `pg_dump`를 호스트 cron으로 돌릴지, Kopia의 스냅샷 전 실행 기능(before-snapshot action)으로 돌릴지
3. **사진 포함 여부**: `/data/nas/photos`를 백업에 포함할지. 용량이 크면 클라우드 비용이 커짐

보관 위치부터 정하면 나머지는 거기에 맞춰 정하면 됨

# 아 kopia는 분산백업이야?

> 아 kopia는 분산백업이야?

## 답변

아님. Kopia는 **스냅샷 백업 도구**이고, 백업 데이터는 저장소(repository) 한 곳에 저장됨

## Kopia의 동작 방식

- **스냅샷 백업**: 지정한 디렉토리를 시점별 스냅샷으로 저장
- **중복 제거**: 바뀐 부분만 새로 저장해서 매일 백업해도 용량이 크게 늘지 않음
- **암호화**: 저장소에 올라가는 데이터가 전부 암호화됨. 클라우드에 보내도 업체가 내용을 볼 수 없음
- **저장소 위치**: 로컬 디스크, SFTP, S3, B2, WebDAV, rclone 등 한 곳을 고름

여러 노드에 데이터를 쪼개 나눠 저장하는 Ceph 같은 분산 스토리지와는 다른 개념

## 헷갈렸을 수 있는 부분: 서버 모드

"서버 모드"는 분산이 아니라 **중앙 집중**

- choimory-server에 Kopia를 띄우면 웹 UI와 저장소 서버 역할을 함
- 원하면 맥북 같은 다른 기기도 이 서버를 통해 같은 저장소에 백업할 수 있음
- 여러 기기가 저장소 하나에 모이는 구조

## 여러 곳에 보관하고 싶다면

Kopia 자체는 저장소 하나만 쓰지만, 복사본을 만드는 방법이 두 가지 있음

1. **`kopia repository sync-to`**: 저장소 전체를 다른 위치로 복제. 예를 들어 주 저장소를 클라우드(B2)에 두고 춘천 본가 PC로 sync하면 두 곳에 보관됨
2. **스냅샷 정책을 두 벌 운영**: 저장소를 두 개 만들어 각각 백업. 관리할 게 늘어서 1번이 더 간단함

3-2-1 원칙(복사본 3개, 매체 2종류, 1개는 외부 보관)을 맞추려면 이렇게 구성 가능

- 원본: 서버의 `/data/...`
- 주 백업: 클라우드 저장소(B2 등)
- 보조 백업: `sync-to`로 외부 디스크나 춘천 본가 PC

# 서버에 저장하는게 아니라 다른저장소에 2차 백업하는거잖아 그니까

> 서버에 저장하는게 아니라 다른저장소에 2차 백업하는거잖아 그니까

## 답변

맞음. **Kopia는 서버에서 실행되지만, 백업 데이터는 서버가 아닌 다른 저장소에 저장함**

## 구조

```txt
choimory-server
├── 원본: /data/apps, /data/nas/photos ...
├── /data/backup: DB 덤프를 모아두는 임시 위치 (백업 아님)
└── Kopia 컨테이너: 원본을 읽어 스냅샷 생성
        │
        ▼ 암호화해서 전송
외부 저장소 (B2, S3, 외장 디스크, 본가 PC 등)  ← 실제 백업이 저장되는 곳
```

- **서버에 남는 것**: Kopia 설정과 캐시(메타데이터)뿐. 캐시는 지워져도 저장소에서 다시 받으므로 백업 데이터가 아님
- **`/data/backup`**: 백업 저장 위치가 아니라, Immich `pg_dump` 결과를 Kopia가 가져가기 전에 모아두는 곳
- **서버 디스크가 죽었을 때**: 외부 저장소에 Kopia를 연결하고 저장소 비밀번호만 넣으면 복원 가능. 그래서 **저장소 비밀번호는 서버 밖에 따로 보관**해야 함. 서버에 있는 Vaultwarden에만 넣어두면 서버와 함께 잃어버릴 수 있음

# 백업 보류

> 서버랑 서버에 향후 연결할 das외에 저장할 다른 스토리지는 없어서 그럼 포기해야겠다 일단

## 답변

일단 보류하는 건 괜찮음. 다만 **완전히 포기하기보다는 DAS가 생기면 다시 도입하는 걸** 권함

## 나중에 DAS가 생기면 의미가 있음

같은 서버에 연결된 DAS라도 서버 SSD와는 물리적으로 다른 디스크

- **막아주는 것**: SSD 고장, 실수로 지운 파일, 잘못된 업데이트로 깨진 설정. Kopia는 스냅샷이라 과거 시점으로 되돌릴 수 있음
- **못 막는 것**: 화재, 도난, 정전 피해처럼 서버와 DAS가 함께 망가지는 경우
- **주의할 점**: DAS를 `/data/nas`에 마운트할 계획이라, DAS에 있는 사진과 미디어를 같은 DAS에 백업하는 건 의미가 없음. 실제로 백업 효과가 있는 건 SSD에 있는 `/data/apps`와 DB 덤프

## 작은 데이터만 클라우드에 보내는 방법

- `/data/apps`와 DB 덤프는 보통 몇 GB 수준
- B2 같은 클라우드는 1TB에 월 몇 달러 수준이라, 이 정도 용량이면 비용이 거의 들지 않음
- 영상이나 사진처럼 큰 데이터는 빼고, **잃으면 복구할 수 없는 것만** 보내는 구성
- 정확한 요금은 도입할 때 확인 필요

## 지금 바로 해둘 만한 것

- **Vaultwarden**: 서버가 죽으면 비밀번호를 전부 잃을 수 있어 가장 위험함. Bitwarden 앱에서 볼트를 주기적으로 내보내기(암호화된 JSON)해서 맥북에 보관해 두는 걸 권함
- **Immich**: 아이폰 원본이 남아 있는 동안은 위험이 낮음. 다만 아이폰에서 사진을 지우기 시작하면 백업이 없는 상태가 됨

## 정리

- 백업은 보류하고 이번 작업 범위에서 뺌
- DAS를 연결할 때 Kopia를 다시 검토함. 저장소를 DAS에 두고, `/data/apps`와 DB 덤프를 백업하는 방식
- 그 전까지는 Vaultwarden 볼트를 수동으로 내보내 보관함
